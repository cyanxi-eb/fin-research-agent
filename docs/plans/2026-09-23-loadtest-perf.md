# 服务并发压测与瓶颈归因（2026-09-23）

> 目的：给简历补一组**可复现、口径明确**的性能数字，同时回答面试高频题
> 「Agent 链路耗时很长时，如何定位性能瓶颈」——用真实验证代替口头方法论。
> 脚本：`scripts/loadtest_perf.py`（分档压测）· `简历/tools/diag_bottleneck.py`（端点对比归因）
> 原始数据：`eval/loadtest_auth_off_bm25_20260923-210101.json`

## 1. 压测口径（先说清楚，数字才有意义）

| 项 | 值 |
|---|---|
| 被测服务 | `fin-research-agent` v0.8.0，本机 `uvicorn` **单进程单 worker** |
| 形态 | `FA_AUTH_ENABLED=0`（免鉴权，隔离掉 JWT 验签开销） |
| 检索模式 | `RETRIEVE_MODE=bm25`（默认基线；未开 hybrid，避免把 embedding API 延迟混进来） |
| 大模型 | **不调用**（SSE 场景固定 `use_llm=false`，走"检索 → 引用 → 校验 → 审计"离线链路） |
| 语料 | 3161 chunk / 5 公司 / 6 公司-年度；向量库 3161×1024（本场景未参与检索） |
| 客户端 | `httpx.AsyncClient`，连接池 2×并发，预热 3 次后计时 |
| 端口 | 8011（独立实例，不干扰日常 8000） |

> 为什么固定 `use_llm=false`：真实 LLM 调用的方差极大（本次实测单次 1–10s+），
> 会把**服务自身的并发能力**淹没在模型延迟里。压测要测的是"我们自己写的这部分"。

### 2.2 端点对比归因（每档 60 请求，压测结束后的独立复测）

| 端点 | 成本性质 | 并发 1 P50 | 并发 10 P50 | 并发 30 P50 | QPS 天花板 |
|---|---|---|---|---|---|
| `/api/citations` | 纯内存（静态说明，不查库） | 33 | 217 | 756 | **~32** |
| `/api/compare` | SQLite 取数 + 工具层 | 88 | 570 | 1413 | **~16** |
| `/api/health` | 聚合 9 个子系统状态（读文件 + 查库） | 177 | 978 | 3532 | **~8** |

## 3. 结论（这一节是面试可以直接讲的）

**① 吞吐天花板由"每请求 CPU 成本"决定，三档呈明显阶梯**：纯内存端点 ~32 QPS、DB 取数 ~16 QPS、健康检查 ~8 QPS。
健康检查比纯内存端点慢 **6 倍**，因为它在每次请求里聚合 9 个子系统状态（索引规模、向量库、法规库、重排、Checkpointer、审计、鉴权、联网兜底、前端），其中含文件状态检查与多次 SQL 查询。

**② 并发到达 10 时系统已进入排队区**：延迟随并发**线性增长**而 QPS 不涨（33 → 217 → 756ms / QPS 持平 32）。
这是典型的"到达率 > 处理能力"排队特征，而不是某个慢查询 —— 因为**连不查库的纯内存端点也一起变慢**。

**③ 故瓶颈不在检索计算、也不在 SQLite 查询，而在单进程内的执行模型**：
`uvicorn` 单 worker + 同步端点被丢进 `anyio` 线程池 + GIL 争用 + 每请求固定开销（依赖注入、Pydantic 校验、鉴权依赖、日志）。
证据链：纯内存端点 QPS 仍只有 32，说明限制来自进程级并发度而非 IO。

**④ SSE 端点的 TTFB 才是用户感知指标**：空载 TTFB P50 **110ms**（检索 + 引用生成 + 校验），
并发上来后 TTFB 与总时长同步劣化（并发 30 时 TTFB P50 7.05s），说明 SSE 的 `async def` + `asyncio.to_thread`
虽然没堵死事件循环，但线程池同样被同步检索吃掉。

## 4. 据此给出的改造方向（方案，未实施）

| 优先级 | 动作 | 预期效果 |
|---|---|---|
| P0 | **多 worker**（`uvicorn --workers N`，配 `--limit-concurrency`） | 突破单进程 GIL 天花板，QPS 近似线性到多核上限；代价是 Checkpointer/审计需确认跨进程安全（SQLite 写锁 → 上 MySQL） |
| P0 | **健康检查改缓存快照**（后台定时刷新，端点只读内存） | 该端点从 177ms 降到毫秒级，避免"排查工具本身成为负载" |
| P1 | **审计异步批写**（队列 + 批量落库），旁路不占请求路径 | 去掉每个 SSE 请求的同步写库成本 |
| P1 | **SSE 检索结果按 (问题, 语料版本) 短 TTL 缓存** | 重复问题直接复用，TTFB 降到毫秒级 |
| P2 | 压测纳入 CI（`scripts/loadtest_perf.py --scenario compare`，设 QPS 回归基线） | 性能回退可见，而不是等到线上 |

## 5. 复现命令

```bash
# 1) 起独立实例（免鉴权形态，端口 8011）
cd fin-research-agent
FA_AUTH_ENABLED=0 RETRIEVE_MODE=bm25 .venv/Scripts/python.exe -m uvicorn src.server:app --port 8011

# 2) 分档压测（三场景：health / compare / stream，结果落 eval/）
.venv/Scripts/python.exe scripts/loadtest_perf.py --base-url http://127.0.0.1:8011 --scenario all

# 3) 端点对比归因（纯内存 vs DB vs 聚合）
python ../简历/tools/diag_bottleneck.py --base-url http://127.0.0.1:8011 --concurrency 1,10,30
```
